# Client architecture

The Server stores authoritative declarations and immutable Artifact bytes. The client reads them, chooses only operations it understands, asks for appropriate user authority, and verifies every download. Local state records what this client has downloaded or performed; it never alters the Server's meaning. Independent clients can implement the same Server contract without this repository.

## Decision records

### ADR-001: Rust core, egui adapter

Use a native Rust core with an egui desktop UI on Linux. The four-platform roadmap is defined in ADR-016. A CLI uses the same core for diagnostics and conformance. The current workspace implements the M1.1 read-only HTTP core and CLI, M1.2 profiles/catalog cache, M1.3 File transfer, M1.4 Tree transfer and the M1.5 desktop adapter. Future modules/crates are introduced when concrete later responsibilities exist:

| Boundary | Responsibility |
| --- | --- |
| Protocol transport | HTTP, Bearer header, pagination, exact JSON/uint64 handling, RFC 9457 errors, capability negotiation; no UI or filesystem policy. |
| Domain/interpreter | App, Release, Association, Artifact and declaration scope; raw JSON retained beside typed recognized views; explicit support assessment. No filename-based inference. |
| Transfer engine | Durable jobs, sequential bounded file transfers, Range/If-Range, SHA-256, Tree Identity v1, path safety, atomic completion. |
| Local library | Profiles, snapshots, jobs, verified content and offline views; storage transactions and recovery. |
| Runtime and launch | Core prepares a separate writable Linux copy from verified immutable objects, assesses NativePortableV1 readiness, and starts a direct process from the declared target and working directory. CLI and egui share this lifecycle. |
| GUI/CLI | Commands and read models from core. GUI renders grid/table, details, queue and eligible Play; CLI exposes capability checks, catalog, download diagnostics and explicit launch inspection/execution. |

The core exposes synchronous operations and durable state snapshots. The desktop crate sends commands to a worker that performs HTTP, SQLite and hashing off the UI thread; separate transfer threads use the existing core jobs, and the UI receives events and refreshed snapshots. Artwork has a separate bounded fetch/decode worker so a slow image cannot stall catalog operations. The CLI is a first-class consumer, so another UI would not require splitting logic out of egui. The protocol itself remains language neutral.

### ADR-002: Explicit identity and selection

Generate a stable local `ServerProfileId` on profile creation; key all Server-local records by it and the Server ID. URL is editable and never used as identity. Keep separate App, Release, Association, Artifact and declaration revision IDs. A shared Artifact digest may reuse verified bytes internally, but access and display context remain profile/association scoped. Do not merge two Server profiles because their digests match.

Show every eligible Release and every association. Optional channels are labels/pointers; no implicit `stable` or `latest`. A Release version is display text, not a total ordering key. Platform-free Artifacts remain visible and downloadable. Unknown platform tokens are visible as unassessed; only recognized, explicitly mapped tokens can produce a compatibility verdict. No association is “primary” unless a future shared declaration explicitly establishes that concept.

### ADR-003: Download is independent of installation and launch

Model `Download`, `Install`, `RuntimePreparation`, `Launch` as distinct operations. `DownloadedVerified` means the delivered Artifact matched its published content identity; it does not describe mutable installation bytes or software safety. A target-only legacy entry point is inert; the optional Association entry-point `NativePortableV1` launch object specifies direct process execution. Keep unsupported declarations visible. A deliberate Play or CLI launch is required, followed by safe declared path resolution. Integrity verification of an installation is an explicit operation, never an implicit Play step. Server metadata is not device authorization.

### ADR-004: Capability-aware compatibility

At connection, read `/capabilities`; retain unknown fields, check the API major/version policy and identity formats actually required for requested operations, and check `downloadRanges`. Never infer support from the Server product version alone. If a capability is absent or incompatible, show catalog where safely possible and disable only affected operations. Do not treat current `apiVersion: 1.0.0` as a stable product 1.0 guarantee. Future declaration operations need their own versioned, shared vocabulary; unknown versions remain opaque.

### ADR-005: Credentials

Use the OS secure store (Secret Service on Linux, Credential Manager on Windows, Keychain on macOS) for Bearer tokens, with an opaque credential reference attached to one local profile ID. Keep profile metadata and token references in the library database; never serialize tokens into jobs, logs, crash reports or exports. If secure storage is unavailable, offer only session-memory tokens or anonymous access. An explicit user opt-in may use a passphrase-encrypted local vault in a later milestone after its format and recovery policy are specified; plaintext fallback is prohibited. Use HTTPS for remote servers by default; allow loopback HTTP for local development and explicit user override for self-hosted LAN endpoints with a clear transport warning. Do not send credentials across a redirect to another origin.

### ADR-006: Local identity, cache and profile removal (M1.2)

SQLite schema version 1 stores each profile under a generated UUID and scopes Apps, Releases, associations, Artifacts and declaration snapshots by that ID. A profile URL change creates a new profile ID and archives the old one; this keeps old cached declarations attached to their original origin. Profile removal requires `--confirm`, removes its secure token, and archives the profile and cache. Archived profiles remain readable offline but cannot synchronize. No M1.2 command deletes cached metadata or verified content. A successful sync fetches the reachable catalog first, then writes it in one transaction. Unseen records are retained and marked stale; a failed fetch does not partially replace the cache. The Server provides a consistent declaration snapshot per Release, not a globally atomic catalog snapshot.

### ADR-007: File transfer and cross-filesystem completion (M1.3)

Use one staging file and a local advisory job lock for each File Artifact transfer. Store a synchronized byte checkpoint and SHA-256 prefix digest in SQLite, then rehash that prefix on resume before issuing `Range` with a strong `If-Range` validator. A matching `206` must identify the exact remainder; a `200` restarts from zero. Keep objects and user-visible materializations under the same content root so hard links provide atomic no-replace promotion without another full copy. Synchronize file and content directories before committing `Completed` in SQLite; reconcile an interrupted `Committing` state by re-verifying the bytes. Metadata and content roots may be on separate filesystems, so no cross-filesystem transaction is assumed. Reuse verified object bytes across profiles while retaining separate profile/association records. This is a local storage decision, not a Server protocol field.

### ADR-008: Tree inventory and atomic materialization (M1.4)

Fetch the entire unfiltered inventory with the Server's page limit and opaque cursors. Require one strong ETag, canonical order, valid file IDs and exact Tree Identity v1 before writing destination paths. Persist the complete inventory and per-member checkpoints in schema version 3. A member file uses the same Range/If-Range/SHA-256 receiver as a standalone File Artifact but becomes only an immutable local object; it is never registered as a separate Association. Construct the visible tree from verified objects in a private staging directory on the content filesystem, preserving explicit empty directories and only the portable executable bit. On Unix, create paths relative to directory descriptors with `openat`/`mkdirat` and `O_NOFOLLOW`. On Linux, `renameat2(RENAME_NOREPLACE)` promotes a verified tree without replacing another destination. Synchronize files and directories before the SQLite Completed transaction; reconcile Committing after a crash by re-verifying the destination or rebuilding from verified objects. Other platforms need an equivalent no-replace directory promotion before Tree completion is enabled. Tree identity is verified independently of destination naming compatibility.

### ADR-009: Desktop command and snapshot adapter (M1.5)

Keep the desktop application in its own workspace crate. UI commands select a profile, synchronize, manage credentials, start or control a specific association job, reveal a verified local path or explicitly Play a ready launch candidate. Worker events provide immutable views of cached Apps, Releases, associations, jobs, verified content and transient process state. The worker owns library access; transfer and launch threads open their own library handles and use the existing core operations. Play carries the displayed Association declaration revision, so a refresh that changes the choice before the worker acts requires the user to review it again. The UI polls durable download progress and never infers completion from network callbacks. Artwork requests use documented App artwork routes, capped response bytes and decoded dimensions, and a profile/App/role/binding-keyed in-memory texture cache. Binding changes invalidate textures on synchronization. Missing artwork is optional. This adapter adds no Server protocol fields or installation authority.

### ADR-010: Offline-first desktop presentation and bounded refresh (M1.5.1)

Keep presentation choices in a small owner-only JSON file beside the local database: system/light/dark theme, grid/list view and last profile ID. Do not store tokens there. First-run connection performs a background capability and catalog-access check before creating a profile. A private catalog asks for an existing personal API token; the Server Account page is opened through a validated origin. The token is verified before being placed in native secure storage or session memory. A secure-store failure leaves session-only access available without a plaintext fallback.

Selecting a profile reads its cached catalog immediately. The worker refreshes the active profile after connection or credential change, when stale at startup or switch, after a sufficiently long foreground absence, and on a 10-minute periodic freshness check. Each profile has at most one sync in flight. Transient failures use capped exponential delay with jitter; HTTP 429 waits at least 60 seconds. Authentication and other persistent failures stop automatic retries until an explicit refresh or credential change. Results carry profile identity so late events cannot replace another profile's view. A failed or partial Server traversal leaves the prior committed cache intact. This policy is a client freshness choice, not a Server snapshot guarantee or implicit payload download. The UI remains responsive because preflight, synchronization, artwork, SQLite and transfers run outside the egui thread.

### ADR-011: Small-member transfer and live observations (M1.5.2)

Keep durable job checkpoints as the recovery authority. The shared receiver emits session-only byte observations after staging writes; desktop workers rate-limit these events to about seven per second per job. The GUI derives a smoothed rate from network-byte deltas and monotonic time. It displays an ETA only with enough measured data and a known remaining byte count, and clears rate/ETA outside active transfer. Received bytes may lead the synchronized SQLite checkpoint; after restart, the staged prefix is revalidated against the durable record. Neither live observations nor a full progress bar imply a verified Artifact.

For Tree members of at most 64 KiB over HTTP, request `Connection: close`. On the isolated Server this avoided a measured roughly 40 ms delay per small body on a persistent connection. Large files and HTTPS retain connection reuse, avoiding repeated TLS handshakes. This is an HTTP transport choice, not an App Depot protocol extension. Tree member lookup uses an indexed progress query; aggregate progress advances by a checked delta in the same SQLite transaction as the member checkpoint. Small members can skip the final staging checkpoint: their verified object is synchronized before the transaction marks the member verified. A crash before that transaction may re-download the uncommitted member but can never report it complete. SHA-256, Tree Identity v1, path checks, no-replace promotion and final completion remain mandatory.

### ADR-012: Linux native portable launch (M2.1)

The core reads the cached consistent Release declaration snapshot, preserves raw JSON and assesses every Association entry point against the exact NativePortableV1 method and platform intersection. It never selects by order. A completed verified File or Tree reference must match profile, Association and Artifact identity. A separate writable installation is prepared automatically after a compatible download or transparently at first Play for an older download. Local readiness checks use no-follow directory traversal; immediately before direct process creation, the opened executable is checked for regular-file type and executable mode, without hashing or size comparison against the original Artifact. The process uses the opened inode and a descriptor-bound working directory, with literal argv and App Depot secrets removed from its environment. The desktop worker starts and waits outside egui; the CLI waits and reports exit status. Spawned process identity is recorded for removal safety after restart. No Server contact is needed for a cached offline launch. Closing the desktop does not intentionally terminate a child. This adapter is Linux-only; other platform launch behavior is unsupported until validated.

### ADR-013: Managed writable runtime and local removal (M2.2)

The verified object store and downloaded materializations retain strict Artifact identity. NativePortableV1 preparation creates an independent writable installation at `apps/<local-installation-id>` from object bytes; Linux uses FICLONE when supported and a checked copy otherwise. A writable hard link to an immutable object is prohibited. `userdata/<local-installation-id>` owns only data created under that managed path. The optional Server declaration does not authorize launch or dictate cleanup of host files. Launch checks the declared target's safe path and executable type inside the installation; it does not claim byte-for-byte verification of mutable files. Explicit Verify integrity reports missing, modified and unexpected paths. Confirmed Repair preserves the prior installation in managed staging and restores original files from verified objects while keeping managed user data.

Version 4 of local SQLite records preparation, removal intent and process identity. Version 5 adds durable queue rank and scheduler-preemption intent to download jobs. One library-wide download slot coordinates GUI and CLI transfers across profiles; the latest explicit request leads the pending queue, and an active transfer yields at a durable checkpoint. User-paused jobs remain paused; preempted jobs requeue after the active process releases the slot. SQLite uses WAL, a bounded busy timeout, short write transactions and a serialized schema-open lock. Normal removal preserves verified downloads and managed data; complete removal drops the selected local reference and data after explicit confirmation. A lifecycle lock coordinates local preparation, Play and removal. Removal traverses only derived managed paths through no-follow directory handles and refuses nested mounts. A mark-and-sweep pass retains file objects referenced by other profiles, Associations, jobs or Tree members. Legacy Tree corruption is isolated per item; explicit source repair rebuilds from verified objects and preserves the old directory in quarantine. Linux defaults new libraries to `~/.appdepot`; a marked XDG library remains active until explicit source-preserving migration. This is a local client contract, independent of Server declaration semantics.

### ADR-014: Desktop presentation and window shell (M2.3)

The Linux desktop uses an undecorated, explicitly resizable eframe window with a custom egui titlebar. Window move, minimize, maximize, close and interactive edge resize issue eframe viewport commands; close still follows the existing active-download confirmation. Edge and corner direction is determined directly from the pointer position inside the viewport, so resize initiation does not depend on an egui overlay's hover hit test; the pointer shows the corresponding resize cursor. The Linux compositor performs the resize through winit. Other operating systems retain native decorations until their window behavior is validated. The titlebar, compact sidebar, responsive content area and settings share a small desktop-only palette and typography module. Light and dark palettes are explicit; System follows the desktop theme. Body, small, button and technical text sizes are set once, while a bounded UI zoom preference multiplies egui's native DPI scale rather than replacing it. Preferences remain in the owner-only JSON file beside library metadata, with no credentials.

Catalog grid/list share the same filtered App set. The details header offers direct Play when exactly one locally applicable launch candidate exists and identifies its Release and entry point; several candidates require explicit selection. Direct Download appears when the App has one Release with one available Association and no Play candidate. All Release and Artifact choices remain explicit below. My Library groups verified references by App while keeping each Release/Association and its management actions separate. Its fixed-height grid cards and compact list rows keep Play visible; a shared action builder supplies pointer-position right-click menus and discoverable More menus without expanding cards. Management actions retain their original worker commands and destructive confirmations. Browse list rows reserve a trailing status zone so descriptions cannot displace it. Downloads keeps active work and the queue prominent, places queue metadata below the name, and keeps completed/cancelled history compact without deleting durable jobs. Settings discloses credential management and identity-changing operations separately; storage bars compare logical categories against the largest category and never claim physical usage or reclaimable bytes. Technical IDs and raw declarations remain available behind disclosure controls. Presentation state cannot mark a transfer complete, execute a declaration, or change Server semantics.

### ADR-015: Official AppImage distribution and updater (M2.4)

The release build embeds a numeric workspace version, Git revision and official build marker. A pinned Ubuntu-based GitHub Actions workflow builds a Type 2 Linux x86_64 AppImage with fixed desktop/AppStream identity and icon sizes. The dedicated desktop updater queries only official stable GitHub Releases; it never uses a configured App Depot Server or its Bearer token. It requires the exact architecture-specific asset, GitHub's asset SHA-256 digest and a matching checksum asset, then stages verified bytes beside a supported user-owned AppImage. A separate helper performs a hash-rechecked atomic exchange after the desktop exits and retains the prior image for recovery. Development and package-managed binaries have no in-place update path. The local library, credentials and download queue are outside the AppImage and outside the updater's write scope. See [DISTRIBUTION.md](DISTRIBUTION.md) for the release and activation procedure.

### ADR-016. SteamOS Decky and the four-platform strategy (M3.0)

| Platform | Client strategy |
| --- | --- |
| Linux Desktop | Maintain the existing AppImage and egui catalog, library and application management. |
| SteamOS | First new platform. Steam Library is the catalog and Play surface, with a small Decky control surface and a Rust wrapper. |
| Windows Desktop | Second new platform. Reuse the Rust core and broadly the same desktop UI, with platform adapters. |
| macOS Desktop | Third new platform. Reuse the Rust core and broadly the same desktop UI, with platform adapters. |

All clients use the authoritative App Depot Server protocol and declarations. The core remains independent of Steam and Decky.

#### Catalog, identity and ownership

Each completed catalog sync supplies one Steam shortcut per accessible App for the configured Server profile, including missing, Windows, generic, data-only and unsupported Apps. Availability and execution support are distinct. Failed or partial sync cannot authorize destructive changes. Keep local content and cached declarations on lost access. Defer detailed stale-entry and removal UX.

Scope the binding ledger by Steam account, immutable local Server profile ID and Server App ID. Keep actual Steam shortcut AppID, an ownership marker and the last values App Depot wrote. Store the selected Release, Association, entry-point and declaration revision independently of shortcut identity. Derive local installation status from the core. Bind artwork by role, source revision and last applied derivative. Changing a profile origin produces a different identity.

NonSteamLaunchers seeds binary VDF AppIDs with CRC32 of the executable string followed by the display name, with bit 31 set. VDF stores the same bits in a signed integer. Artwork filenames use unsigned decimal. Recomputing after rename or target change can produce another AppID. Preserve the stored ID when editing fixtures and capture the actual ID returned by Steam when creating live. The fixture models distinct stable target paths so equal display names can coexist. It rejects true numeric collisions. Verify a practical live collision strategy before committing to the target layout.

Only modify a shortcut when a saved binding matches a unique observable ownership marker. Never adopt by name, executable, numeric ID or tag alone. Missing or ambiguous proof stops that operation for diagnosis. Preserve foreign entries, unknown fields, user launch options and compatibility settings. Apply a Server rename only when the name still equals the last written value. Artwork uses the same conflict principle. Release changes invalidate an affected selection or require an explicit new choice. Unknown metadata remains inert. For live creation, persist pending intent and re-read before retrying to prevent duplicates after a crash.

NonSteamLaunchers uses internal SteamClient.Apps methods including AddShortcut, SetShortcutName, SetShortcutExe, SpecifyCompatTool and SetCustomArtworkForApp. Prefer a feature-detected live adapter after hardware validation. These interfaces have no public stability contract established by the reviewed projects. Capture readback after changes and restart. Binary shortcuts.vdf editing is limited to disposable fixtures in M3.0. Any future file fallback requires positive Steam shutdown detection, a fresh read, backup, atomic replacement and a persistence test. A lock used by another tool cannot serialize Steam's own writes.

#### Decky, storage and deployment

The Server panel handles setup, authentication, profile, refresh and sync errors. Installed shows local status and leaves room for later removal. Settings shows integration health, library root and diagnostics. Decky Loader supplies the frontend/backend RPC, reads dist/index.js and runs an optional Python main.py. The Python layer can supervise a user-level Rust worker with typed operations. Rust owns credentials, catalog, transfers, runtime and launch. Steam-facing calls only consume bounded typed values. Never concatenate Server text into executable arguments or scripts.

Use Decky's settings and runtime directories for plugin state and keep the App Depot library outside replaceable code. Package versioned plugin binaries and validate upgrading a stable user-owned wrapper path with live bindings intact. Run as the selected Steam user. Unload cancels sync tasks and detaches the integration bridge. Already running games retain their own wrapper lifetime. Reattach after a plugin or Steam restart and read back the active account's state.

Default to the existing marked Linux library or ~/.appdepot for a new one. Use writable home paths. For microSD, validate mount identity, execution, hard links, atomic promotion and free space before enabling a content root. Keep SQLite metadata on internal storage initially and treat an unmounted card as unavailable. Multiple libraries are deferred. Reuse existing SQLite WAL and schema, library access, job and lifecycle locks. One durable download queue and shared transfer slot coordinate wrapper, Decky and Desktop. M3.1 must pick a scheduler ownership and reattachment model that preserves checkpoints and explicit pauses without independent transfer workers. Validate native secure storage under the Steam user in Gaming Mode. [SteamOS writable storage](https://help.steampowered.com/en/faqs/view/671a-4453-e8d2-323c)

#### First Play and session

The stable native wrapper resolves explicit App Depot identity and cached selection. Present a choice only when needed among Releases, Associations and entry points. Download missing content through the core, verify SHA-256 and Tree Identity v1 where applicable, prepare a writable runtime and launch the declared executable. A ready runtime starts from cached state without networking or rehashing local changes. When an uninstalled App cannot reach its Server, show Retry and Exit. A small controller-friendly egui window is a candidate for selection, progress and errors. Hide or close it when handing off focus to the game.

The wrapper waits for the core-spawned process, using literal arguments, with no intermediate shell. Steam remains responsible for controller mappings. Linux process waiting is locally testable. On a real Deck validate overlay, focus, playtime, Stop Game and signals, descendant lifetime and return to Steam. Verify built-in controls and Steam Controller and check that controller configuration survives rename and restart. [Steam Deck FAQ](https://partner.steamgames.com/doc/steamhardware/steamdeck/faq) · [Steam Input devices](https://partner.steamgames.com/doc/features/steam_controller/device)

#### Windows and Proton

Show Windows Apps in every successful catalog sync. A stable native target has no established handoff to Steam's selected Proton for a Windows child. A mutable target could let Steam apply Proton on a later Play, with AppID, Input configuration, compatibility tool, prefix and the current session all needing verification. NonSteamLaunchers explicitly sets compatibility or prefix information for its own launchers. That does not establish an in-session native-to-Proton transition. Test both strategies without distributing or managing Proton. Keep unsupported Windows execution inert with a clear explanation. If a Server extension is needed, propose a separate optional declaration with Windows target, platform, literal argument list and relative working directory. Steam would continue choosing the tool. NativePortableV1 retains its existing meaning. [Valve Proton](https://github.com/ValveSoftware/Proton)

#### Artwork

Map Server roles steam.grid.vertical, steam.grid.horizontal, steam.hero, logo (fallback steam.logo) and icon to their Steam equivalents. In userdata/<account>/config/grid the reference PNG names are <appid>p.png, <appid>.png, <appid>_hero.png and <appid>_logo.png. The icon is referenced by path. SteamGridDB filters include portrait 600×900, wide 460×215 or 920×430 and hero 1920×620. These are test inputs, with Steam's acceptance and scaling subject to hardware validation. SteamGridDB lists PNG, JPEG, WebP and ICO depending on role, uses a PNG upload for live artwork, and prompts for Steam restart for its non-Steam icon path.

Preserve Server bytes. Cache a deterministic grayscale derivative for the two uninstalled grids, preserving alpha. Switch to original colors after install. Key cached derivatives by role, source digest or binding revision, and transformation version. Update only App Depot-owned artwork when its binding changes and no local override is detected. Test cache invalidation per role and across restart. Shortcut creation and play remain usable if artwork is missing.

#### Feasibility and development

The headless command app-depot --profile ID first-play APP_ID RELEASE_ID ASSOCIATION_ID ENTRY_POINT_ID requires explicit cached selection. It shares the Rust transfer, preparation and launch paths. The loopback harness exercises authenticated catalog reads, exact artwork bytes, verified Tree download, runtime preparation, literal arguments, supervised process lifetime, catalog rename and offline replay after modifying the installed executable. Existing real-Server tests cover declaration round-tripping and File/Tree Range resume and CLI recovery after SIGKILL. Binary VDF fixtures cover idempotence, stable rename, equal names, preservation of foreign settings and refusal on ambiguous ownership or collision. Artwork fixtures exercise mapping and color/grayscale placement. No Steam process reads these fixtures.

Use Client Rust 1.95.0 with rustfmt and clippy and the Server's pinned Rust 1.88.0. The Server web build uses Node 26.5.0 and npm 11.17.0. Debian dependencies include build-essential, pkg-config, libssl-dev and libdbus-1-dev. For fixture tests also install python3-vdf and python3-pil. From the Client checkout with Server as a sibling:

~~~sh
(cd ../app-depot-server && cargo build -p app-depot-server --locked)
cargo build -p app-depot --locked
/usr/bin/python3 -B -m unittest discover -s tools/steamos -v
/usr/bin/python3 -B tools/steamos/verify_first_play.py --server "$PWD/../app-depot-server/target/debug/app-depot-server" --client "$PWD/target/debug/app-depot" --client-repo "$PWD"
~~~

The harness uses an OS-assigned loopback port, a fresh temporary namespace and synthetic credentials. It stops the process and removes its temporary data on exit. Omit --client-repo to run only the fixture and First Play flows. The native fixture is x86-64 Linux. The CLI currently reports transport/queue failures in the terminal. Controller UI, automatic selection and interactive retry are follow-up work. See [M3.1](MILESTONES.md#m31--steamos-integration) for hardware acceptance.

### M3.1a implementation

The installable Decky release candidate and hardware acceptance procedure are documented in [SteamOS Decky](STEAMOS_DECKY.md). The packaged CLI's Decky feature adds user-level RPC operations, a native First Play window, a worker scoped to verified preparation, and supervision of the core-spawned game. Decky synchronizes through the Rust CLI. The frontend uses private SteamClient methods and checks live details before applying changes to a bound shortcut. The backend verifies artwork revisions and preserves user overrides using the last managed Steam file digest. An atomic ledger and a read-only Steam snapshot support ambiguous-create recovery. No platform dependency enters the Rust core.

## UI read model

Catalog grid and list share one filtered data set. Cards emphasize App name, optional artwork/description and local availability; missing optional metadata uses a neutral fallback. Details show all Releases and associations with individual download actions and Play only for a locally applicable NativePortableV1 candidate. One unique local candidate can lead the App page even when other Release or Association choices exist; its identity is displayed beside Play. Explicit platform/runtime/entry-point declarations remain visible; raw exact JSON and IDs remain in Advanced sections. Library groups File and Tree references by cached App identity. Right-click and More expose the same per-Association actions, with technical properties nested in the menu. Open Folder targets the writable installation when present and the verified download otherwise. Downloads shows durable progress and per-member Tree details, with compact history rows. UI status distinguishes cached metadata, current connection health, transfer state, verified local bytes and process state. A verified download is not necessarily launchable or installed. No Release, channel, executable or primary Artifact is inferred.

## Trust boundaries

Limit response sizes, artwork dimensions/cache and concurrent transfers. Parse exact uint64 values. Validate inventories before materialization: no absolute, traversal, backslash, NUL, invalid UTF-8, duplicate, case-fold/normalization collision, special-file or destination-reserved names; use safe directory handles or equivalent anti-symlink checks. Reject an unrepresentable tree instead of renaming it. Only materialize verified bytes, and never execute them during validation. Render declaration text as inert text. NativePortableV1 arguments are passed as separate argv elements without a shell; target and working directory stay within the verified Artifact tree. See [LOCAL_LIBRARY.md](LOCAL_LIBRARY.md) for storage and recovery.
