# Conformance and integration plan

Use the Server OpenAPI as the route/schema source and `docs/tree-identity.md` vectors as identity fixtures. Pin the tested Server commit and record the capabilities response in test output. Tests run against a separately initialized Dev/Test Server data root and a temporary client library, with disposable users/tokens and deterministic fixtures. Never connect integration tests to Production or reset an existing user library. The client has no privileged test-only bypass.

## Contract tests

| Area | Required cases and expected behavior |
| --- | --- |
| Catalog/auth | Anonymous enabled/disabled, Public Published read, Bearer owner Private/Draft read, inaccessible Private 404, missing token 401, forbidden visible action 403. Paginate Apps, Releases, associations and revisions; invalid cursor `400 invalid_cursor`; query/scope changes invalidate cursor. |
| Capabilities | Supported identity formats/ranges; missing or unknown fields, different API version, advertised lower page limit and incompatible identity format yield explicit partial/unsupported state, never silent fallback. |
| Declarations | Missing, null, scalar, unknown fields and incomplete entry points; raw JSON survives typed projection. Multiple associations and points remain distinct. Validate declared target: valid, missing, not-file, invalid and unsupported. No entry point remains downloadable without Launch. |
| Discovery/selection | Optional channels, no channel, multiple Releases, multiple Artifacts per Release; no implicit primary or guessed latest. Platform absent is visible; unsupported platform/runtime and unsupported installation method are explained without execution. |
| Artwork | Missing role 404 gives placeholder; valid image displays, wrong/oversized/unsafe content is rejected locally; private artwork obeys authorization. |
| File identity | Download a file including zero-byte file, verify exact length and SHA-256 against `adfile:sha256`. Hash mismatch never reaches Completed. |
| Tree identity | Fetch all unfiltered inventory pages; verify paths, fileId opacity, sizes, hashes, executable flags, explicit empty dirs and v1 vectors. Reject traversal, absolute paths, backslashes, duplicate/case/Unicode collisions on target filesystem, symlink destinations and special/unrepresentable names. Do not repair path spelling. |
| Resume and HTTP | Interrupt mid-file and mid-tree, restart process, resume validated bytes. Matching `If-Range` 206 with exact `Content-Range`; mismatching validator/full 200 restarts file; 416 revalidates; truncated body or wrong range fails. Multiple-range full 200 is accepted only as a full restart. Bounded retries for transport/429/503; clear terminal errors for 400/401/403/404 and digest mismatch. |
| Local persistence | Completed files offline, incomplete jobs recover, committing-state crash recovery, no false Completed after interrupted fsync/rename, two profiles with same remote IDs stay separate, shared bytes retain independent contexts, local removal does not delete another reference. |
| Launch safety | Legacy target-only points remain inert. NativePortableV1 requires exact Linux host platform, effective Release/point intersection, explicit Association and entry-point selection, completed verified local content, confined no-follow target and working directory, executable type/mode and target SHA-256 at launch. Literal argv never uses a shell; unknown methods, malformed values, symlink escape, changed bytes and unavailable content fail closed. CLI and GUI process states and offline launch are tested separately from Server target assessment. |

## Test layers

1. Pure unit tests for identity/path validation, JSON preservation, compatibility assessment and transfer state machine, using Server Tree Identity v1 positive and negative vectors.
2. HTTP contract tests driven by OpenAPI shapes and isolated Server fixtures, including error bodies, ETags, exact integer parsing, pagination and Range semantics.
3. Process-level interruption tests with real temporary library and real Dev Server: kill client during transfer/commit, restart and verify recovery. The Server's existing `crates/server/tests/upload_http.rs` is evidence for Server behavior, not a substitute for client download tests.
4. Linux GUI smoke tests for catalog, details, queue and offline library. Windows/macOS filesystem and secure-store checks run when those platform milestones start.

No test should execute arbitrary downloaded software or modify Production Server state. Launch tests may execute only a scoped synthetic fixture in a disposable library. A fake HTTP server is appropriate for malformed responses and adversarial paths; real Server tests remain required for the actual protocol.

## M1.1 implemented coverage

The read-only core tests cover capabilities and unknown fields, exact large integers, Bearer versus anonymous requests, RFC 9457 errors, expired/repeated cursors, multi-page traversal, multiple associations, safe URL encoding, refused redirects and malformed/oversized responses. `crates/app-depot-core/tests/real_server.rs` is deliberately ignored in routine runs and requires an isolated published fixture when invoked with `--ignored`; it reads capabilities, catalog, Artifact metadata and the consistent declaration snapshot without mutating the Server. Native launch unit tests cover declaration projection and a scoped synthetic Linux process, including literal arguments, working directory, secret removal, nonzero exit, tampering and symlink rejection. The Server's isolated HTTP tests cover normative declaration assessment separately.

## M1.2 implemented coverage

The local-library tests create/reopen the version 1 foundation, reject unknown schemas and unsafe roots, distinguish profiles with equal remote IDs, archive old identities on URL change/removal, reject unavailable native storage without plaintext fallback, preserve full JSON integers, fetch a mock catalog and commit it atomically, roll back on a database error, keep prior cache after a failed paginated fetch, mark unseen records stale after a complete later sync, and read cached metadata offline. The ignored real-Server test additionally syncs an isolated Published fixture into a temporary client library, reopens it, and checks the declaration value `u64::MAX`. Linux Secret Service was exercised with a disposable token and the token was removed.

## M1.3 implemented coverage

File transfer tests cover empty and ordinary files, SHA-256 mismatch, truncation, process-style interruption and reopening, matching `206`, full `200` fallback, invalid ranges, `416`, missing/changed ETag, authorization failure, bounded transport retry, destination locking, interrupted commit reconciliation, object reuse, two profiles sharing content, offline verified-file access, corrupt staging, SQLite completion failure, and version 1 to version 2 migration. The ignored real-Server test downloads a Published File Artifact larger than 64 KiB through an isolated loopback Server, pauses after a checkpoint, asserts a real `206` and `Content-Range`, reopens the disposable library, resumes and verifies the completed file. M1.3 was validated with Server checkout `08c749b1124624d33af38a99e03d24ad45ee8564` advertising `apiVersion: 1.0.0`, `fileIdentity: adfile:sha256` and `downloadRanges: true`.

## M1.4 implemented coverage

Tree tests use Server Tree Identity v1 positive logical vectors V1–V9 (V7/V8 duplicate V1/V2) and applicable logical negative vectors N8–N13. Binary-stream corruption vectors N1–N7 and ZIP ingestion mapping N14 belong to the Server's canonical parser/ingester; the client receives JSON inventory and independently emits the canonical hash stream. Client tests reject missing parents, duplicate paths, unsupported types, case/Unicode collisions, destination-reserved names, malformed pages, weak/changed inventory ETags, repeated or invalid pagination, unsafe symlinks, missing/changed object bytes, database completion failure and duplicate active jobs. They verify empty/nested directories, executable flags, no-replace materialization, offline access, cross-profile content reuse, version 2 to 3 migration and Committing recovery. The shared File/Tree receiver inherits M1.3 adversarial Range, If-Range, size, SHA-256 and retry tests.

The ignored real-Server Tree test uses a separate Published fixture with three files, a nested directory, an executable file, two explicit empty directories and a 1 MiB member. It requests `pageSize=1` to traverse inventory, pauses during the large member, checks a real `206` and `Content-Range`, reopens a disposable library, resumes, checks executable mode and lists the tree offline. The ignored Linux `tree_sigkill` integration test places a slow loopback proxy in front of the isolated Server, sends `SIGKILL` to the CLI during a partial member transfer, reopens the library, verifies Paused with previously verified members retained, resumes to Completed and lists the tree after stopping the proxy. It requires `APP_DEPOT_TEST_TREE_ASSOCIATION_ID` in addition to the real-Server test variables. The Server checkout was `08c749b1124624d33af38a99e03d24ad45ee8564`; capabilities advertised `apiVersion: 1.0.0`, `treeIdentity: adtree:v1:sha256`, `fileIdentity: adfile:sha256` and `downloadRanges: true`. The Published fixture was seeded only into a disposable Dev catalog/CAS and served through the real Server endpoints; upload registration itself is covered by Server tests. Windows/macOS Tree filesystem tests remain for later milestones.

## M1.5.2 transfer performance and telemetry

Benchmark procedure: use a disposable copy of an isolated Dev/Test Server data root and a fresh client metadata/content root for each cold run. Serve on loopback with Server commit `08c749b1124624d33af38a99e03d24ad45ee8564`; anonymous reads are enabled only in the copy. Generate deterministic SHAKE256 payloads keyed by fixture name and file index, register them as Published File/Tree Artifacts with complete declaration documents, and verify the canonical Tree identities before transfer. Workloads are one 16 MiB File; a Tree with four approximately 8 MiB files; a Tree with 1,000 distinct files of 2,048–2,174 bytes; and a mixed Tree with 500 such small files plus four approximately 4 MiB files. Include explicit empty directories. Time CLI `download start` with `time.perf_counter` around the process invocation, excluding fixture generation and profile creation. Compare baseline `ff2d4e8` with the M1.5.2 build using fresh roots and the same warm Server cache. The figures below are single runs on the CachyOS host with a Btrfs client content root and a tmpfs Server CAS; they are evidence for this host, not LAN or TrueNAS predictions.

| Workload | Bytes / files | Baseline | M1.5.2 | Effective complete-job throughput |
| --- | ---: | ---: | ---: | ---: |
| Large File | 16 MiB / 1 | 0.701 s | 0.712 s | 22.46 MiB/s |
| Few large Tree members | 32.01 MiB / 4 | 2.590 s | 2.292 s | 13.96 MiB/s |
| Many small Tree members | 2.01 MiB / 1,000 | 59.940 s | 19.105 s | 0.11 MiB/s |
| Mixed Tree | 17.01 MiB / 504 | 33.427 s | 11.286 s | 1.51 MiB/s |

For an already verified 1,000-member Tree referenced by a second profile, the new job took 8.309 s with no member transfer; this includes object revalidation, per-association metadata and a separate verified materialization. A 16 MiB File paused at a synchronized 4,198,400-byte checkpoint in 0.366 s and resumed to completion in 0.658 s. A mixed Tree paused at 1,050,693 verified bytes in 8.203 s and resumed in 3.152 s without losing completed members. These timings include normal process startup and recovery checks. The existing ignored real-Server File/Tree tests and Linux SIGKILL Tree test validate Range resume and offline completion separately.

Component measurements used monotonic clocks without per-file logging. Direct persistent-connection HTTP reads of 100 small members took 4.281 s (0.257 s to headers, 4.024 s to bodies); explicit close took 0.121 s (0.117 s to headers, 0.004 s to bodies). The 1,000-member persistent run spent 2.691 s waiting for headers and 40.386 s reading bodies. A 16 MiB File request spent 0.270 s before headers and 0.074 s reading its body. The Server implementation hashes the entire CAS object before responding, but these timings alone do not isolate that hash from authorization and scheduling. Capabilities took 1.53 ms to headers, catalog 0.71 ms, and the 1,002-entry inventory took 11 pages with 24.64 ms total header wait plus 0.06 ms body read on the same loopback host.

An instrumented run of the final transfer logic on Btrfs measured the 1,000-member Tree in 19.388 s: 2.589 s waiting for member headers, 0.242 s in the body receiver (including 0.022 s staging writes and 0.079 s streaming SHA-256), 0.116 s rehashing staged files, 11.932 s promoting synchronized objects and committing member metadata, 0.135 s inventory retrieval/validation, and 3.650 s final Tree materialization/validation. The remainder includes metadata lookups, staging preparation and process overhead. In the mixed Tree, the corresponding combined object-promotion phase took 6.207 s of an 11.185 s run. These component intervals are not all additive: staging writes and streaming SHA are nested inside the body receiver. Temporary timing instrumentation and screenshots stayed outside the repository.

The measured small-response delay is an HTTP connection interaction on this Server build; `Connection: close` for HTTP Tree members no larger than 64 KiB removed it without changing the Server contract. Btrfs object synchronization remains the largest measured local cost after that change; relaxing durability to hide it is not acceptable. Sequential transfer and per-member authorization remain future performance limits. Production TrueNAS throughput, Windows/macOS filesystems and HTTPS behavior were not benchmarked. A separate Server task could measure whether response coalescing or socket options remove the small persistent-connection delay while retaining full CAS verification; no Server change is included here.

## M2.1 native portable launch coverage

Core tests assess a cached Release snapshot with multiple Associations, a legacy target, a supported method, an unknown method, an unknown platform token, malformed arguments and an exact `uint64` unknown value. Linux process tests use only disposable synthetic executables; they check literal argv, declared working directory, secret removal, nonzero exit, changed bytes, non-executable mode and symlink/path rejection. Existing File/Tree transfer tests remain in the workspace suite.

An isolated Server at M2.0 commit `156404cab91801ac5e82cf5d60981b945efdbe83` was exercised through its real HTTP implementation with disposable File and Tree Artifacts and `NativePortableV1` declarations. Its read-only assessment returned `Valid` for both; the client synchronized, downloaded, verified SHA-256 and Tree Identity v1, assessed both as Ready and directly launched both from the temporary library. A second launch succeeded after the Server was stopped. The File upload protocol has no portable executable bit, so this synthetic File was explicitly made executable by the test user after verification; the client did not change its mode. The Tree inventory declared its executable member and materialization applied that portable flag. The native Wayland GUI was manually exercised against a disposable offline library: Play started a synthetic process, the user could navigate to My library while it ran, and the exit code appeared afterward. These checks establish process creation and lifecycle UI behavior, not graphical gameplay compatibility with Unreal Gold.

## M2.2 managed local library coverage

Disposable core tests construct cached File and Tree Associations, verified immutable file objects and synthetic Linux programs. They check both File and Tree preparation/launch, independent runtime inodes, runtime writes without changes to original bytes, running-process removal refusal after reopening the library, normal removal retaining managed data and verified content, offline runtime restoration, and complete removal of owned data. A second fixture checks that a data-only File shared by two profiles survives the first local removal and is reclaimed after the last owner is removed. Tree source inspection reports an unexpected legacy runtime file as an item-level issue while an unrelated verified File remains available; explicit repair rebuilds from verified objects and retains the former directory in quarantine. Migration tests copy separate metadata/content roots, refuse an open source library, and preserve an unexpected regular file in an old materialization without modifying the source. Existing File/Tree transfer, launch and CLI tests remain in the workspace suite. Process-level SIGKILL tests interrupt removal after the durable `Removing` transition and migration during staging copy, then reopen or retry against disposable roots. An isolated loopback Dev/Test Server with disposable Published File and Tree fixtures passed all three ignored real-Server tests (catalog/declarations, File Range resume, Tree Range resume) and the Tree SIGKILL recovery test. A separate disposable CLI library successfully synchronized this Server, downloaded and removed a File Association, then migrated to a new root while preserving the source. Native Wayland startup and populated Browse windows were visually inspected online and offline; cached Apps remained visible when the Dev/Test Server was stopped. Real-game behavior, production data cleanup, Windows/macOS adapters and complete interactive desktop workflows remain unverified; no Production Server or real user library is an automated target.
