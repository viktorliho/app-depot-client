# Linux AppImage distribution and updates

The supported binary distribution is a Type 2 `x86_64` AppImage built on Ubuntu 24.04 with Rust 1.100.0. This is a compatibility baseline, not a promise that every Linux distribution or compositor works. Linux supplies glibc, graphics drivers, Wayland/X11 integration and a usable desktop session. AppImage's Type 2 runtime may need FUSE 2; `--appimage-extract-and-run` is a manual fallback. Secret Service remains the preferred credential backend. Persistent profiles, downloads, installations and preferences remain in `~/.appdepot` or an explicitly configured library, never in the AppImage.

## Install

Download `AppDepot-VERSION-x86_64.AppImage` and its `.sha256` file from the [official client releases](https://github.com/viktorliho/app-depot-client/releases). Verify with `sha256sum -c AppDepot-VERSION-x86_64.AppImage.sha256`, make the AppImage executable and run it. Gear Lever can integrate this same file into the user application menu. The desktop ID is always `io.github.viktorliho.AppDepot.desktop`; the icon name and AppStream ID use the same stem. The packaged desktop entry supplies `X-AppImage-Version`, which Gear Lever displays. Keep one integrated copy. The updater replaces the current user-owned AppImage path, so the desktop entry can continue pointing to it.

## Versions and publication

Stable Desktop releases use one annotated `vMAJOR.MINOR.PATCH` tag matching the workspace version and identifying one verified main commit. The owner accepted the first unified stable release, v0.1.4, on Linux and Windows. Release jobs build and test Linux x86-64 and Windows x64 independently from that commit. The workflow creates a draft only after both jobs succeed and verifies the exact asset set and GitHub digests. The required set is the versioned AppImage, its `.sha256` and `.zsync`, `AppDepot-Desktop-Windows-x64-Setup.exe` and `SHA256SUMS`. The publication job uses GitHub Actions permissions to publish the verified draft as stable and set it as Latest. Existing releases and tags are immutable under this procedure. Decky publishes independently. macOS joins the set when officially supported.

`scripts/build-appimage.sh` pins appimagetool 1.9.1 and its Type 2 runtime by SHA-256 and refuses mismatched downloads. The AppDir has `AppRun`, the desktop executable, update helper, `.desktop`, AppStream metadata and PNG icon sizes. It embeds `gh-releases-zsync|viktorliho|app-depot-client|latest|AppDepot-*-x86_64.AppImage.zsync` and publishes the corresponding `.zsync` asset for external AppImage-aware tools. The built-in updater uses full downloads; delta updates are not required for correctness.

## Built-in updater

Only an official AppImage running from a user-owned regular file in a user-owned directory can update in place. Development, extracted AppDir and package-managed builds may check official releases but offer only the release link. The checker runs at startup and at most every six hours while the app is open, independently of App Depot Server profiles. It accepts only a newer stable numeric version, the exact `x86_64` asset name and URL, GitHub's SHA-256 asset digest and a matching published checksum file. Requests use HTTPS, explicitly follow only approved GitHub release-asset redirects, and enforce response media types, sizes and timeouts. The trust root is the official GitHub repository and TLS; this protects against transport corruption and untrusted mirrors, but compromise of that GitHub release authority is outside this initial model. No private signing key is embedded or claimed.

The published v0.1.0 and v0.1.1 AppImages contain a redirect-handling defect: GitHub's normal release-asset `302` response is interpreted as the checksum body, so their built-in update check cannot complete. The published checksum is valid; changing release notes or metadata cannot repair those already distributed binaries without replacing immutable assets. To move to v0.1.2, download its official AppImage and checksum, verify with `sha256sum -c`, and replace the existing integrated AppImage through Gear Lever. Keep the same integrated application path and desktop ID; do not install a second launcher entry. The corrected updater in v0.1.2 can handle later stable-release asset redirects.

Update downloads stage beside the installed AppImage, verify length, SHA-256 and Type 2 format, then wait for explicit **Update and restart**. The button is unavailable while a transfer, local operation or managed game is active. A separate helper waits for the launcher to exit, verifies the old and new hashes again and writes and synchronizes a checked previous-version backup **before** atomic exchange on Linux. It launches the replacement directly and waits for its first UI frame to acknowledge startup. If spawn or acknowledgement fails, it exchanges the files back and starts the prior version. A helper interruption still leaves the previous version at the explicit backup path; if recovery is needed, close App Depot, inspect the installed and backup AppImages with `--version`, then restore the backup with an ordinary file-manager operation. The helper never overwrites an existing backup. Desktop v0.1.5 upgrades a v0.1.4 library from SQLite schema 5 to schema 8. This migration is forward-only. Restoring the previous executable leaves the migrated database at schema 8, which v0.1.4 cannot open directly.

If the install directory is not writable or in-place replacement is unsupported, download the official release manually. Do not replace a package-manager-owned executable. The updater does not access the managed library or credentials. Active queue and local operations are not silently cancelled; a user can restart after work finishes. A native program launched independently may continue after App Depot exits, but the updater defers while one is tracked as running.

## Repeatable release procedure

1. Finish an authorized release candidate on `main`, review the full diff and run `cargo fmt --check`, `cargo clippy --workspace --all-targets --locked -- -D warnings`, `cargo test --workspace --locked`, the release desktop build, package validation and graphical smoke checks.
2. Confirm the version has no existing tag or release. Prepare accurate release notes. Create an annotated `vMAJOR.MINOR.PATCH` tag at the verified main commit and push only that tag.
3. Wait for the `Desktop release` run to build both platforms, verify the exact five assets and both checksum files, check the embedded versions and source revision, smoke-test the packages and publish the verified draft as Latest. A failed build or verification leaves the release unpublished.
4. Independently download the public assets, verify checksums and metadata and confirm GitHub Latest points to the new complete Desktop release.

If publication fails with a draft present, prefer rerunning the failed job from the original workflow run to retain its verified build artifacts. The retry detects an existing release and requires it to be a draft. If the workflow fails before a release exists, dispatch it with the existing immutable tag (`gh workflow run release.yml --ref main -f tag=vMAJOR.MINOR.PATCH`). For an existing draft, a fresh dispatch requires `-f resume_draft=true`. The retry checks every existing asset against the verified build before uploading missing files. A byte mismatch leaves the draft untouched for review, including a mismatch caused by a non-reproducible rebuild. The workflow rechecks the original tag object and Latest before publication. If the release is already public, inspect its assets and Latest following the normal independent verification procedure. Published releases and source tags remain immutable.

An explicitly assigned Desktop release task authorizes all these steps without separate tag, draft or publication approvals. Routine development on main runs cross-platform CI without triggering a release. Publication uses the workflow token with contents write permission, so a locally authenticated GitHub CLI is unnecessary. No Server deployment or Production library mutation is part of this process.
