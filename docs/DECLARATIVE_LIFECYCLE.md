# Declarative software lifecycle: current contract and gaps

This is an analysis and proposal, not an active Server schema. Server commit audited: `08c749b1124624d33af38a99e03d24ad45ee8564`. The Server stores optional `data` JSON independently on App, Release and Release–Artifact association. `data.appDepot` has typed conventions but arbitrary other JSON survives. An independent client must use the Server's current declarations as authoritative and must never derive an operation from payload bytes, filename, extension, executable flag or embedded metadata.

## Current standardized surface

- **App:** summary, description, kind, developer, publisher, license, homepage URL, tags and categories. `kind` has no required vocabulary or execution meaning.
- **Release:** notes, free-form `platforms` strings (practical `linux/x86_64`, not a normative enum), and `runtime` with optional free-form `name` and `version` strings. No standardized architecture alias or runtime operation.
- **Association:** label, purpose, description, and up to 100 `entryPoints` with stable association-local ID, optional label/platforms, and an explicit target. `ArtifactFile` targets the associated single-file Artifact; `TreeFile.path` is the exact immutable inventory path of a regular file. The Server can assess shape/existence without interpreting launchability. Multiple associations and multiple points are valid. No default point, implicit launch command or required executable bit.
- **Artifact:** immutable file/tree content identity and inventory. Artifact identity has no software semantics.

The Server permits non-object `data`, unknown fields and unresolved declarations. The client must preserve the full raw JSON and display unknown/unsupported parts. A typed view is read-only and partial. Any future editing must round-trip unknown fields and use the current strong ETag; it must never silently replace the document with only recognized keys.

## Lifecycle assessment

1. **Download:** any accessible Artifact may be downloaded, including data-only and platform-unspecified ones. Integrity verification says only that bytes match the Server identity.
2. **Compatibility:** known, explicit platform constraints may be matched to host OS/architecture. Unknown tokens and absent constraints are `Unknown`, not hidden or falsely supported. Runtime names/versions are displayed; no preparation follows from them.
3. **Entry point:** association point target must be valid against the verified Artifact. This describes a candidate file, not a permitted execution method. `Valid` Server assessment is not an authorization decision.
4. **Install:** no current shared operation defines portable versus installer-based software, installation destination, side effects, rollback or external prerequisites. M1 reports `Installation required` only when a future recognized contract supports that conclusion; otherwise `Install method unspecified/unsupported` is accurate. No automatic dependency installer.
5. **Launch:** requires a future supported execution declaration and user action. M1 never presents a functional Launch action. Data-only Apps/Artifacts need no entry point and remain successful downloads.

## Smallest shared extensions to evaluate after M1

| Use case / existing scope | Sufficiency of current JSON | Smallest candidate contract and compatibility rules | Independent-client implementation |
| --- | --- | --- | --- |
| Match OS and CPU: Release-wide baseline, narrower Association/entry point | `platforms` is present but free-form and lacks architecture grammar/aliases. | Standardize a versioned token vocabulary and matching rules for existing Release/entry-point `platforms`; allow unknown tokens and no platform field. Add Association-level constraint only if one Release contains distinct platform Artifacts needing filtering independent of entry points. Keep all associations visible. | Parse known tokens exactly; report unknown/unsupported; do not guess from Artifact name. |
| Portable program requiring no install: Association-specific | No portable marker or execution contract. | Optional typed `distribution`/`preparation` method with a defined `Portable` value at Association scope, versioned and explicit; no field means unspecified. Define whether materialization alone is enough and which platform rules apply. Do not require it for data-only Artifacts. | Recognize Portable, verify bytes, materialize safely; otherwise show downloaded/unsupported procedure. |
| Explicit file target: Association | Existing `entryPoints` and target types suffice for locating bytes. | Keep target grammar; add validation requirements for path confinement and binding to associated Artifact. Future execution fields must reference an entry-point `id`, not duplicate paths. | Resolve `ArtifactFile` or exact `TreeFile.path` only from verified inventory. |
| Working directory and argv: individual entry point | Undefined. | Optional typed launch descriptor on an entry point: working directory expressed as Artifact-relative directory or a specified safe value; arguments as an array of literal strings with defined substitution policy (prefer none initially). Define argv encoding, path restrictions and version. No shell command string. | Pass argv elements directly to a supported process API; validate path and reject unsafe/unresolved substitutions. |
| Runtime requirement/preparation: Release baseline or entry-point override | Current `runtime.name/version` describes free-form text; no detection, fulfillment or precedence. | Define a small, versioned runtime identifier/constraint vocabulary and optional supported preparation method in the relevant scope; keep legacy free-form object readable and non-executable. Specify override semantics only if needed by a concrete multi-runtime Release. | Report installed/unsupported/unknown runtime via a platform adapter; prepare only a declared recognized method after consent. |
| Installer-based release: Association | No procedure, target or side-effect contract. | Add optional versioned `installation` method descriptor for a specific association, with a typed installer family and artifact target, explicit scope/elevation/uninstall semantics as needed. Add each family only for a demonstrated use case; no universal script schema. | Implement a selected family in an OS adapter, show scope/elevation effects, ask user, record outcome. Unknown family stays downloadable. |
| External prerequisite/redistributable: Release or specific entry point | Free-form runtime cannot express detection source or vendor identity. | Optional typed prerequisite ID, version constraint and user-facing source/requirement; preparation method only if explicitly standardized. Avoid auto-download or implicit trust in arbitrary URLs. | Detect through a named adapter; report missing requirement and user action. No automatic installation in initial milestones. |
| Dependency detection and preparation: operation-specific | Undefined; a text list would not justify execution. | Versioned detector and preparation operation IDs with portable semantics, capability names and consent requirements. Start with a narrow case when the Server contract has a real publisher use case. | Advertise supported operations; fail closed on unknown IDs; present a manual path for unsupported requirements. |
| Data-only Artifact/App | Already valid with optional metadata. | No extension. Absence of entry points/install metadata is a normal state. | Download, verify, show contents/metadata and no Launch action. |
| Multiple Artifacts and entry points | Existing association IDs and point IDs suffice for structure, but default selection/execution precedence is undefined. | Preserve all; if a default is ever needed, define an explicit Association/entry-point reference at Release scope with ambiguity and platform rules. Do not infer primary from order. | Offer explicit user selection; match only supported declared options. |

For any future extension, update Server architecture/API/OpenAPI, validation and tests in one separate authorized task. It must remain optional, versioned, data-only compatible, losslessly round-trippable and executable only by clients that declare support. Server validation may assess syntax and references, but the client owns local safety, user consent and execution. No proposal above authorizes arbitrary shell scripts or automatic package installation.

Open decisions for that later task: define a portable OS/architecture vocabulary and unknown-token behavior; decide whether a point needs an explicit launch method separate from its file target; choose the first concrete portable or installer use case; define working-directory and argument encoding without shell interpretation; and specify how multiple eligible points are selected. None blocks the download-focused MVP.
