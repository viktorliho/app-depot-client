# Declarative software lifecycle

The Server's [Native portable launch v1](https://github.com/viktorliho/app-depot-server/blob/main/docs/architecture.md#native-portable-launch-v1), API and OpenAPI define the shared protocol. App, Release and Association declarations remain independently versioned JSON documents. The client preserves their full values, including unknown fields and exact JSON integers. An Artifact's bytes, name and executable flag never create software semantics.

## Current supported operation

An Association `data.appDepot.entryPoints[]` item may carry `launch: {"method":"NativePortableV1","workingDirectory":"System64","arguments":[]}`. Its existing `target` is the only executable target: `ArtifactFile` for a File Artifact or an exact `TreeFile.path` in verified inventory. A point without `launch` is a non-executable file reference. The method is a direct native process operation; it is not an installer, shell script, runtime preparation instruction or permission grant.

The point must have nonempty `platforms`. Known v1 tokens are `linux/x86_64`, `linux/aarch64`, `windows/x86_64`, `windows/aarch64`, `macos/x86_64` and `macos/aarch64`. Matching is exact and case-sensitive. A nonempty Release `data.appDepot.platforms` further intersects the point's known set. Unknown tokens remain stored but have no v1 match. Only Linux x86_64 and aarch64 have an execution adapter in the reference client; Windows/macOS declarations remain readable and inert here.

`workingDirectory` is relative to the Artifact root. Omission uses the target file's parent; the empty string selects the root. For a File Artifact, only root is valid. A nonempty Tree directory must be present as a Directory entry in verified inventory. `arguments` defaults to `[]`; each item is a literal UTF-8 argv string, including possible empty strings. There are at most 64 arguments, at most 4096 UTF-8 bytes per item and 16384 bytes total. Controls, shell parsing, substitutions and environment expansion are unsupported.

The client reads a consistent cached Release declaration snapshot and keeps each profile, App, Release, Association, Artifact and entry-point ID separate. It assesses all points; no filename, array order, channel or version picks a default. If several compatible points exist, the user selects an Association and entry-point ID explicitly. A newer synchronized declaration replaces the cache for future assessment; a desktop Play command is bound to the displayed Association declaration revision and rejects a changed revision instead of silently changing targets. Offline launch can use a cached snapshot and locally verified content without contacting the Server. Cache age and local integrity remain distinct.

Before Linux execution, the client requires a completed verified local Artifact reference for the selected Association, checks target and working directory against the immutable inventory, opens every local path component without following symlinks, checks regular-file type, expected size and executable mode, then rehashes the opened executable against its expected SHA-256. This recheck covers the selected target, not a claim that the entire Artifact was freshly reverified at process start. The existing library listing also validates completed File/Tree content when constructing readiness. Tree inventory carries a portable executable flag; the BareFile upload contract does not, so a downloaded File without executable permission remains unavailable for Play until the user explicitly supplies that permission. The client never changes a File target's mode merely because a launch declaration exists. A direct native process is started from the opened inode with the declared working directory and literal argv; App Depot token, secret and SSH-agent environment variables are removed. The UI does not block while it starts or waits. Closing the launcher does not intentionally terminate a running child. Every Play is explicit user intent.

Unknown methods, malformed declarations, platform mismatches, absent or corrupted local bytes, unsafe paths and non-executable targets remain visible as unavailable. They do not prevent downloading or opening the local folder. The Server's read-only target/launch assessment informs publisher editing but does not establish client execution readiness or authorization.

## Remaining contract gaps

Release `runtime.name/version` is descriptive only. There is no standardized installation, dependency preparation, Wine/Proton, environment override or system package operation. Data-only Artifacts need no launch metadata. Any future executable method requires a separate optional shared Server contract and explicit client support; arbitrary shell commands are not part of this method.
